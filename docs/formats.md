# Vordr — file formats and security model

This document specifies the three on-disk formats and states the security
guarantees (and their limits) honestly. Constants live in `src/macros.inc`.

All three formats reuse Myrkr's proven container discipline:

- a fixed header used **verbatim as the GCM AAD**, so header tampering breaks
  authentication;
- a **key-check value** `KCV = SHA-256(key)[0..15]`, so a wrong master password
  is rejected immediately after the KDF (and the construction is
  key-committing);
- fresh **CSPRNG** salt/nonce per write (`rng_fill` = OS CSPRNG ⊕ RDSEED);
- **atomic writes** via a temp file + `MoveFileExW`.

---

## 1. Vault file `.vordr` (magic `"VRDR"`, v1)

One encrypted file holds the entire vault. On unlock it is decrypted into
`secmem` (VirtualLock'd) memory; on change it is re-sealed and atomically
replaced.

```
VAULT_HDR (64 bytes, = GCM AAD):
    magic       dd   "VRDR"
    version     dd   1
    t_cost      dd   Argon2id passes        (default 3)
    m_cost_kib  dd   Argon2id memory KiB     (default 524288 = 512 MiB)
    lanes       dd   Argon2id parallelism    (1)
    salt        db32 CSPRNG salt
    nonce       db12 GCM nonce
KCV             db16  SHA-256(key)[0..15]
body            AES-256-GCM( serialized entry stream )
tag             db16  GCM tag
```

**Body plaintext** is a length-prefixed record stream (no JSON/CRT parser):
vault meta (entry count, created/modified `FILETIME`) followed by entries. Each
entry is a 16-byte random id + timestamps + TLV fields
`{u16 type, u32 len, bytes}` for title / username / secret / url / notes / tags
(`VF_*` in `macros.inc`). Every length is `BOUND_CHECK`ed against
`MAX_FIELD_BYTES` / `MAX_ENTRY_BYTES`.

Key: `Argon2id(master password, salt, t, m, p=1) → 32-byte AES-256 key`.

## 2. One-time pad `.vpad` (magic `"VPAD"`, v1)

Pre-shared OTP key material that both parties possess. A pad **is** key
material, so it is stored **encrypted at rest** under the vault key and only
decrypted into `secmem` when sharing/opening.

```
header: magic | version | pad_id db16 | total_len u64 |
        consumed_offset u64 | source (CSPRNG | TRNG)
body:   AES-256-GCM( pad bytes )    ; encrypted at rest
```

- `consumed_offset` is a **local high-water mark**: pad material below it has
  been used and must never be reused. This is the single invariant on which OTP
  security rests.
- `source` records whether the pad was generated by the app CSPRNG
  (`PAD_SRC_CSPRNG`, *computationally* secure) or imported from an external true
  RNG (`PAD_SRC_TRNG`, *information-theoretically* secure).

---

## 3. Share file `.vshare` (magic `"VOTP"`, v1)

An OTP-encrypted secret destined for a holder of the matching pad.

```
header (cleartext, non-secret):
        magic | version | pad_id db16 | pad_offset u64 | msg_len u64
payload:
        ciphertext = msg XOR pad[pad_offset .. pad_offset+msg_len]
        tag        = one-time MAC over (header || ciphertext)
```

- The **one-time MAC** (Carter–Wegman universal hashing, `MAC_KEY_LEN`-byte key
  taken from a fresh disjoint pad slice) gives **unconditional integrity**:
  forgery probability is bounded by ~`2^-128` regardless of adversary
  computing power.
- Pad consumed per share = `msg_len + MAC_KEY_LEN`; `consumed_offset` advances
  so the region is never reused.

---

## Security model — guarantees and limits

### Confidentiality / integrity
- **At rest:** AES-256-GCM (AEAD) + Argon2id. Quantum-hardened by construction —
  Grover only halves symmetric strength (→ ~128-bit) and Argon2id's
  memory-hardness is unaffected by Shor.
- **Sharing:** OTP gives information-theoretic confidentiality and the one-time
  MAC gives information-theoretic integrity — provided the OTP rules hold.

### OTP caveats (read these)
The "provably secure / quantum-immune" claim holds **only** when:
1. the pad is **truly random** — CSPRNG-generated pads are *computationally*
   secure, not information-theoretic; only TRNG-imported pads are unconditional;
2. each pad region is used **exactly once** (enforced by `consumed_offset`);
3. the pad is **at least as long** as all data ever shared with it;
4. the pad is delivered to the recipient over a **secure out-of-band channel**.

Pad management (the no-reuse high-water mark) is the critical correctness
invariant; a reuse bug collapses the guarantee entirely.

### Hostile-OS resistance is best-effort in user mode
Vordr raises the cost of compromise — VirtualLock keeps decrypted secrets out
of the pagefile, the IAT is locked read-only, W^X / ASLR / DEP / NX / CET +
software shadow stack / stack canaries / DLPV / tagged heap are all on, and all
key material is `secure_zero`d. But against a **fully compromised kernel** (or a
DMA-capable attacker), user-mode defenses cannot be absolute. We state this
plainly rather than overclaiming.
